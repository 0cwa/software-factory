# Pi Foundry + Software Factory Development Program

This plan summarizes the critical path. The live coordinating issues remain authoritative.

## North star

```text
Pi Foundry prepares and evolves an exact reviewed Pi environment
        ↓
Software Factory exposes and executes inspectable development workflows
        ↓
Pi Protocol enforces capability contracts and canonical receipts
        ↓
Reviewed role/pipeline/executor/tool providers perform bounded phases
        ↓
Factory verifies and opens an evidence-backed draft PR
        ↓
Foundry evaluates/promotes harness changes through exact proposals
```

## Stage A — stabilize Foundry's environment authority

Primary issue: https://github.com/0cwa/pi-foundry/issues/1

Deliver:

- immediate activation/rollback/blocker safety;
- pinned pnpm workspace and clean cross-platform fixtures;
- versioned desired/observed/lock/proposal/transaction schemas;
- conformance tiers and focused infrastructure toolkit;
- actual environment inspection and exact artifact resolution;
- pure resolver/proposal and journaled transactions;
- isolated Pi package/patch backends;
- security, TUI/agent/CLI/update/repair lifecycle.

Factory work must not bypass these foundations with an ad hoc installer.

## Stage B — refocus Software Factory and preserve the reference

Primary issue: https://github.com/0cwa/software-factory/issues/1

Start with:

- #2 preserve the aggregate snapshot and reset product authority;
- #3 independent repository/source modes;
- #4 `.pi/factory/` tracked/runtime root;
- #5 TypeScript/pnpm workspace and module boundaries;
- #6 versioned Factory schemas.

Copied Pi component trees remain reference evidence, not implementation targets.

## Stage C — build the inspectable workflow kernel

```text
software-factory #6 schemas
-> #7 workflow graph/compiler/path views
-> #8 resumable journaled runtime
-> #9 isolated Git worktrees
-> #10 deterministic code/gates/evidence invalidation
-> #11 Pi Protocol adapter
-> #13 prompt/context functions
-> #14 bounded evidence/query/viewer
-> #15 thin interfaces
```

The graph definition drives execution, text/JSON/Mermaid/DOT views, possible-path analysis, safety diagnostics, candidate diffs, and model-based tests.

## Stage D — prove one direct vertical slice

```text
software-factory #12 plan-change/direct-protocol
```

Factory owns the work unit, phases, gates, acceptance, and durable run. Pi-Dev supplies scout/architect roles through Protocol. No mutation occurs.

This is the first architecture proof. Pi-PE and Taskplane are not prerequisites.

## Stage E — deliver the primary software workflow

```text
software-factory #16 software-change
```

Required shape:

```text
plan
-> isolated implement
-> deterministic tests/checks
-> bounded same-session fixes
-> independent review
-> bounded revisions
-> rerun invalidated checks
-> explicit acceptance
-> draft PR / retained candidate
```

Factory becomes the reviewed default `development.workflow`; Foundry issue #31 enforces one top-level authority.

## Stage F — variants and migration

- Factory #17: selectable variants/authority contract;
- #18: evaluated Pi-PE subpipeline variant;
- #19: evaluated subordinate/top-level Taskplane variants;
- #20: SSSF import/parity/compatibility;
- Foundry #30-#33: Factory component, authority, state ownership, sibling sources.

Promote variants from evidence, not presumed abstraction value.

## Stage G — self-evolution and evaluation

- Factory #21: isolated workflow/prompt/harness candidates;
- #22: held-in/held-out multi-objective evaluation;
- #23: protected evaluator/permission/promotion boundary;
- Foundry #29/#34: normalize and compare Factory evidence;
- Foundry #35: private developer harness overlay.

Candidates may edit only explicit surfaces and cannot edit their own evaluator, permissions, budgets, traces, promotion policy, or active state.

## Stage H — low-input issue-to-draft-PR development

- Factory #24: dependency-aware GitHub issue program;
- Factory #25: layered developer-harness configuration;
- Foundry #36: issue-specific capability assembly.

The reviewed flow is:

```text
select ready exact issue
-> load direct authority/context
-> Foundry inspect/verify or propose minimum capabilities
-> approve/apply/reload/verify
-> bind environment receipt
-> Factory isolated plan/build/test/review
-> draft PR and issue evidence comment
-> stop for review/merge or exact blocker
```

## Stage I — default dogfood and cleanup

- Factory #26 and Foundry #30 integrate install/init/audit/update/rollback;
- Factory/Foundry cross-platform and fault-injection gates pass;
- developer config moves from transitional branch to private repository;
- Foundry #24 and Factory #28 remove legacy/vendored/stamped duplicate authorities only after parity.

## Program completion

The program is complete when:

- a clean repository can be configured through Foundry with Factory as the default workflow;
- workflows and all meaningful possible/current paths are visible, editable, validated, and recoverable;
- a ready issue can proceed to a tested/reviewed draft PR with little routine input;
- environment, workflow, capability, evidence, and promotion authorities remain orthogonal;
- harness candidates are evaluated against protected held-out/hard gates and promoted only through PR/Foundry;
- independent repositories dogfood exact sibling sources without submodules or portable machine paths;
- old copied/stamped authorities are preserved as history/migration evidence but absent from the normal product path.
